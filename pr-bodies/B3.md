### What
Implements `cairo_ft_font_face_create_for_ft_face`, `cairo_font_face_reference`, `cairo_font_face_destroy`, `cairo_font_face_get_user_data` and `cairo_font_face_set_user_data` following Cairo 1.18.0. This addresses the review of #16892:

- Faces are cached by guest `FT_Face`, `face_index` and load flags, as in `_cairo_ft_unscaled_font_keys_equal` and `_cairo_ft_font_face_create`. A repeated call returns the same face with one more reference and shared user data.
- The face does not take a reference on the `FT_Face`; Cairo does not either.
- An allocation failure returns the nil face (`NO_MEMORY`). No invented status codes are used.
- User data follows `_cairo_user_data_array_set_data`: replacing or clearing a key releases the old data, and an empty slot is reused.
- The last destroy removes the face from the cache, then releases user data in reverse order, so a create from a finalizer gets a new face, as in Cairo.
- Like Cairo's `__put`, the last reference stays while the finalizers run, so a finalizer may reference and destroy the face.
- `cairo_ft_font_options_substitute` is not touched (#16895).

Recorded in the debt file:
- Setting user data on a face from its own finalizer throws, and so does destroying the face there without a reference of the finalizer's own. Cairo modifies or frees what it is finalizing in those cases.
- Cairo's "zombie" face, kept while a scaled font holds the unscaled font, is not modelled, because the scaled-font exports still throw.

`tools/guest_pointer_audit.py` reports the read of `face->face_index`; Cairo reads it directly too.
