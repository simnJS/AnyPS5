### What
Every `malloc`, `free`, `calloc`, `realloc` and aligned allocation locked one process-wide `std::mutex` in `ApplicationHeap.cpp`, only to copy an entry of the allocator table. That table does not change once an allocator is registered. For a title that brings its own allocator, this lock was the one point where all its threads met.

The table is now published through an atomic pointer when it is registered. It is withdrawn when initialization fails or when the heap is finalized, so the locked path still reports those states as before. A second registration of the same table no longer rewrites it under readers.

`aligned_realloc`, `malloc_stats_fast` and `malloc_usable_size` still take the mutex.

### Tested
- Linux (Ubuntu 24.04, GCC 13, Release), 4-core x86-64 VM. **Not measured on a title.**
- New `application_heap_threads` test: four threads, 200000 allocate and free pairs each, through a registered no-op allocator. Five runs each:
  - `main`: 180.7, 181.2, 186.5, 188.0, 182.5 ns per pair.
  - This branch: 6.3, 4.6, 4.7, 4.5, 4.4 ns per pair.
- This is the cost of the lock alone. A real allocator does more work per call, so the gain in a title is smaller and unknown.
